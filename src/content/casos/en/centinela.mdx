## Context

Riwi project (2026) focused on cloud services and architecture on Azure. It remains a working prototype in development, centered on demonstrating the detection architecture and the transaction processing flow.

## Problem

Detect potentially suspicious transactions that may need additional review.

## My responsibility

I took part in building the solution, mainly the infrastructure and backend components on Azure: API, Blob Storage, Service Bus, Azure Functions, Cosmos DB and the identity and permission mechanisms.

## Analysis

Detection was based on rules and a risk threshold: each transaction gets a score, and those above the threshold are flagged as potentially suspicious.

## Solution

An event-driven architecture: the API receives the transaction and publishes it to a Service Bus queue; an Azure Function processes the message, applies the detection logic and stores the result in Cosmos DB for querying and follow-up.

## Implementation

- Infrastructure as code with Bicep.
- Decoupled communication through Service Bus.
- Service-to-service access with Managed Identity and RBAC.
- Networking with Virtual Network.
- Centralized configuration with App Configuration.
- Blob Storage as supporting storage.

## Validation

Test transactions were sent to check the full flow across services: that each transaction was received, processed and stored correctly.

## Result

<Fact value="60" label="risk threshold above which a transaction is considered potentially suspicious" />

The end-to-end flow works in the prototype. No detection or precision rate is reported: that would require a formal evaluation with labeled data.

## Learnings

I learned to design an event-driven architecture with managed Azure services, taking security, scalability and decoupling between components into account.

Today I would start with a more representative test dataset and formal detection metrics, such as precision, recall and false positives.
